# 使用示例

以下均为虚构场景，展示判断方式，不代表这些项目或测试真实存在。命令、文件名与验证结果应替换为实际证据，不能直接作为真实提交的验证记录。

## 同一意图跨多个文件

用户要求提交一次重复请求修复，改动包含服务端幂等判断、前端状态提示和对应测试。这些内容共同实现一个行为，可以属于同一提交。独立的文档拼写修正有不同目的，只有用户也授权提交时才单独处理。

假设本次确实运行了一个测试命令，且 6 个测试通过，可写：

```text
fix(jobs): 避免重复请求创建多条任务

客户端重试可能重复发送同一个请求，需要在服务端识别同一次操作。

实现与决策：
- 使用请求幂等键复用已创建任务，前端据此展示原任务状态。

验证：
- python -m unittest tests.test_jobs：6 个测试通过，覆盖首次创建与重复请求。

边界与后续：
- 幂等键按账户隔离，后续重构需保留这一约束。
```

若只检查了 diff，不能照抄“6 个测试通过”，也不能补写未讨论过的替代方案。

## 用户使用中文，项目要求英文

用户说“帮我写这次修复的 commit message”，项目贡献指南要求英文。技能正文的语言不影响输出；可以使用英文标题和正文：

```text
fix(cache): preserve entries until their expiry time
```

是否补充正文取决于真实复杂度和证据。仅要求“写 message”时，不执行 `git add` 或 `git commit`。

## 项目有自己的标题规范

项目规定标题形如 `Cache: preserve entries until expiry`，并要求正文包含指定字段。使用项目格式，保持意图和证据完整，不强行添加 `fix(cache):` 前缀。若用户明确要求另一个格式，而提交检查不接受，应先说明具体冲突。

## 已暂存内容与本次任务无关

暂存区已有文档改动，工作区还有本次缓存修复。不能直接运行普通 `git commit` 把已有暂存内容一起提交，也不能为方便操作清空暂存区。

应检查并分离本次范围，保留无关内容及原暂存状态。如果无法可靠地隔离，应说明阻塞并保留现场。用户已经明确授权的改动不需要仅因它由其他人编写而重复询问。

## 一条旧提交解释了 fallback，但后来条件改变

旧提交记录“服务端 v1 在部分响应中缺少时间戳，因此保留 fallback”，后来提交移除了 v1 支持。不能只根据旧提交要求永久保留 fallback，也不能仅因 v1 被移除就认定它一定无用。

应继续核对当前协议、所有相关调用方与测试。输出需区分：旧提交明确记录的原因、后续提交改变的条件，以及当前证据能否支持删除。调查本身不授权删除代码。

## 只有标题的普通提交，没有 Entire

历史只写了“修复缓存”，diff 显示调整了过期时间计算。可确认计算方式发生了变化；仅凭这两项无法确认作者曾遇到什么生产故障、评估过哪些方案。

继续检查相关测试、后续提交和已有文档，并说明未找到动机记录。不要要求安装 Entire 才能继续，也不要把合理推断写成已发生的讨论。

## 历史验证与当前验证分开

旧提交写了“单元测试通过”。可以引用为“该提交记录了当时测试通过”，不能输出“当前分支测试已通过”。当前是否通过需要当前运行的证据，且需要说明验证覆盖的对象与环境。

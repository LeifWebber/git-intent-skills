# Git 提交工作流

围绕用户已确认的任务目标，审查相关改动，并按独立的改动意图拟写提交信息、规划提交拆分，或在获得授权后创建 Git commit。

Commit 应被视为项目长期维护及未来 AI Agent 排查问题的重要上下文。提交信息不仅需要说明“改了什么”，更应保留可核实的改动意图、关键设计决策、验证结果和长期影响。

## 1. 适用条件与操作授权

- 仅当用户明确要求“整理并提交”“创建 commit”等操作时，才执行相应的暂存和提交。
- 仅要求拟写、审查或优化提交信息、规划拆分时，不修改工作区、暂存区或 Git history。调用本技能本身不等于授权提交。
- 提交授权默认不包含 push、amend、重写历史、丢弃改动、修改 Git 身份或签名设置，以及绕过 hooks 等检查；这些操作需要单独授权。
- 已经明确授权的目标和操作无需重复确认；只有范围不明、发生冲突或需要额外操作时才询问。

执行前检查适用的项目指令、提交规范和检查要求。发现冲突时明确说明，不静默忽略或绕过。

## 2. 确认范围并保护已有工作

先确认目标仓库、分支及工作区状态，包括已暂存、未暂存和未跟踪的内容，再确定本次提交范围。暂存状态不代表提交授权。

- 以本次任务已确认的目标为边界，**不要提交和本次会话无关的内容**。用户可能在本次会话里和你进行了多轮交流，请你综合所有来理解目标或意图。
- 优先识别本次任务产生的改动，同时识别实现同一目标所必需的已有改动；提交并非你本次修改的内容时，确认用户的授权已明确包含这些内容，否则先询问。
- 根据改动意图判断归属，不简单依据文件位置、暂存状态或修改者判断。
- 不将无关改动、归属不明的修改、意外混入的凭证或临时产物一起提交。
- 同一文件混有相关和无关改动时，仅暂存属于本次范围的部分，不因文件相关就提交整个文件。
- 对范围外的已有改动，保留其内容及暂存状态；不得为方便提交而擅自清空暂存区、覆盖文件或丢弃修改。
- 无法可靠判断归属或安全分离时，保留相关内容并说明阻塞；只处理能够安全完成且语义完整的部分，不猜测、不强行打包。

不要未经范围确认就无差别暂存整个工作区。

## 3. 按独立意图划分 atomic commit

提交应按照独立的改动意图、解决的问题或行为变化划分，而不是按文件、目录、前后端或技术层次机械拆分。

- 为实现同一目标而修改的 UI、API、测试、配置等，通常属于同一个 commit。
- 多个能够独立理解、具有不同目的且可分别回滚的改动，应拆分为多个 commit。
- 仅为某项功能服务的重构或准备工作，不必为了区分 type 而强行拆出；具有独立价值的重构可以单独提交。
- 不要把无关清理、顺手优化或格式化混入功能修复；也不要为了追求“小提交”而破坏语义完整性。
- 每个 commit 应尽可能保持项目处于有效状态，不依赖后续尚未提交的改动。
- 允许存在明确的前序提交依赖，但应按依赖顺序提交；存在重要回滚约束时，应予以说明。

目标是让每个 commit 都能被独立理解，并尽可能独立验证和回滚，而不是让每个 commit 只修改一种文件。

## 4. 提交标题与语言规范

本技能使用中文说明，但不要求生成中文提交。提交信息的语言与格式按以下顺序确定：

1. 用户对本次任务的明确要求。
2. 目标项目的提交规范、贡献指南、适用指令和提交模板。
3. 近期相关提交中稳定的语言与格式惯例。
4. 没有约定时，语言沿用用户当前交流语言，格式默认采用 Conventional Commits。

规范关键字、命令、代码标识符和 API 名称等保留原文。用户要求与项目强制检查冲突时，说明冲突并确认处理方式，不擅自修改或绕过检查。

以下说明采用 Conventional Commits 时的写法；项目使用其他规范时，遵循其格式，同时保留意图、真实决策、验证和边界信息。标题形式如下：

`<type>[(<scope>)][!]: <description>`

其中，方括号表示可选部分，不出现在实际标题中。存在 scope 时使用圆括号，例如：

`fix(auth): 阻止已停用账号通过第三方登录`

采用该规范时：

- 根据改动的实际语义选择 type，不把行为变化伪装成 refactor 或 chore。
- scope 应稳定、简洁，并优先沿用项目已有约定；没有合适的 scope 时可以省略。
- description 优先表达改动目的、解决的问题或系统行为变化。
- 标题保持简洁，较长的背景、原因和取舍放入正文，不要求一行同时容纳所有信息。
- 避免只描述代码操作，例如“修改播放器逻辑”“更新 API”“重构组件”。

存在不兼容变化时，说明受影响的调用方、行为变化及必要的迁移方式。采用 Conventional Commits 时，必须使用 `!` 或 `BREAKING CHANGE:` 标识；采用其他规范时，使用其规定的标识方式，不隐藏不兼容变化。

## 5. 正文：记录关键方案与真实决策

正文首先补充理解本次改动所必需的背景、动机和关键解决方案。

优先记录：

- 为实现目标采用的核心机制和实现路径。
- 关键数据流、状态流或生命周期变化。
- 重要的架构、API、状态管理或兼容性决策。
- 无法仅从 diff 直接理解的实现原因。
- 重要 trade-off，以及确实讨论或评估过的替代方案为何未被采用。

信息必须有依据：

- 意图和决策应来自本次已确认的需求、讨论、实现过程或其他可核实证据。
- 不要仅根据最终 diff，事后编造设计动机、历史背景或方案比较。
- 无法确认的原因宁可省略，不将合理猜测写成已发生的事实。
- 不复述可以直接从 diff 看出的机械性变化，不逐文件罗列修改。
- 不记录与工程决策无关的对话、个人信息或敏感内容。

## 6. 验证：准确说明执行内容与验证范围

如果进行了有意义的验证，在 body 中记录**验证方式和已经确认的行为**，可使用“验证：”小节或目标语言中的对应标题；项目有模板时遵循其组织方式。

- 记录具体命令、手动验证场景或已经确认的行为，必要时补充影响结论的环境条件。
- 只记录实际完成的验证；未执行的测试不得写成通过。
- 区分静态检查、构建、自动化测试与运行时行为验证，不夸大检查能够证明的范围。
- 明确验证对象：对包含全部改动的工作区执行过测试，不代表拆分后的每个 commit 或中间状态都已单独通过测试。
- 验证后若又发生影响结论的改动，应重新验证，或准确注明此前验证的适用范围，不沿用失效的结论。
- 与本次正确性有关的验证失败、阻塞或重要未验证范围，应如实说明；没有证据时，不将失败归因于“已有问题”或“环境问题”。

根据改动风险选择相称的验证，不为填充提交信息执行无关检查，也不为生成完整模板编造验证记录。

## 7. 边界、风险与后续工作

存在值得未来维护者或 AI Agent 注意的内容时，在 body 正文末尾记录，可使用“边界与后续：”小节或目标语言中的对应标题；项目有模板时遵循其组织方式。

优先记录：

- 本次刻意未覆盖的范围及必要原因。
- 当前方案依赖的重要假设、不变量或兼容性约束。
- 对其他模块、接口、数据或生命周期造成的影响。
- 后续重构容易误删或破坏的逻辑，以及必须保留的原因。
- 已知但尚未解决的问题。
- 必要的迁移、清理、技术债或回滚注意事项。

只记录与本次改动直接相关、具有维护价值的信息。

不要为了填满模板臆造风险、扩展需求或添加泛泛建议；不要使用“提高代码质量”“增强可维护性”“改善用户体验”等没有提供额外上下文的表述。

## 8. 正文结构与 footer

没有项目模板时，正文使用自然段或普通小标题组织，各部分之间空一行。小标题与正文使用相同语言。

下面以中文和 Conventional Commits 为例展示可选结构，不要求其他项目采用这些标题或格式：

```text
<type>(<scope>): <目的、问题修复或行为变化>

<必要的背景与动机；没有额外信息时省略>

实现与决策：
- <关键方案、机制或有依据的取舍>

验证：
- <实际执行的检查、结果与适用范围>

边界与后续：
- <重要约束、未覆盖范围、风险或必要后续工作>

<可选的 Conventional Commits footer>
```

没有项目另行规定时：

- 上述结构是可选的信息组织方式，不是必须填满的表单。
- 简单改动可以只保留标题，或标题加简短正文。
- 没有实质内容的小节直接省略，不填写“无”“暂无”或占位符。
- 不使用独占一行的 `---` 或其他装饰性分隔线。
- 提交正文中的小标题不使用 `#`、`##` 等 Markdown 标题前缀；可使用“实现与决策：”“验证：”“边界与后续：”。
- 上述小节及其其他语言版本均属于 body，不作为 Conventional Commits footer。
- `BREAKING CHANGE:`、issue 关联或项目要求的 trailers 放在正文之后，与正文空一行，并遵守相应格式。
- 不编造 issue 编号、审核人、签名或其他 footer 信息。

追求高信息密度，而不是长度。提交信息应补足 diff 缺失的上下文，不承担完整变更日志或对话记录的职责。

## 9. 提交前检查与执行

执行提交时，对每个拟创建的 commit：

1. 明确该提交的单一核心意图及所包含的改动。
2. 仅暂存属于该意图且在授权范围内的内容。
3. 检查实际 staged diff，包括新增、删除、重命名及必要的关联改动，确认没有无关内容、意外删除或遗漏。
4. 确认提交信息与实际 diff、真实决策和已完成的验证一致。
5. 确认语义完整性、前序依赖和已知边界后，再创建 commit。
6. 提交后检查实际提交结果与剩余仓库状态，确认本次内容已正确提交，范围外工作未受破坏。

若 hooks、格式化工具或其他过程修改了待提交内容，重新检查相关 diff，必要时重新验证，不直接将新增变化视为已经审查过。

提交或检查失败时，不擅自绕过检查、扩大修改范围或重写历史。修复属于本次授权范围的问题；超出范围或无法安全处理的情况，应保留现场并说明。

不要仅为完成提交流程顺手引入新的功能、重构或无关修复。

## 10. 完成后的反馈

根据实际执行情况简要报告：

- 已创建的 commit hash、标题及必要的拆分理由；仅拟写或规划时，明确说明尚未提交。
- 实际验证结果及重要未验证范围。
- 尚未提交的相关改动、保留的无关改动，以及需要注意的阻塞或风险。

不要重复粘贴全部 diff 或所有提交正文，也不要把计划中的操作表述为已经完成。

最终质量标准：

未来完全不了解本次对话的维护者或 AI Agent，仅查看该 commit 及相关代码，就应能够理解：为什么改、行为如何变化、采用了什么关键方案、实际验证了什么，以及哪些边界和约束需要继续保留。
